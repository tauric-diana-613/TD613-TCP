### Required service-resolution acceptance model

Treat the three-phase Loom demo as one underlying operator need, not three independent screens.

Define the operator journey as one case identity:

Loom task / source selection
→ Portable AIA preparation
→ Marrowline Phase 2 continuation #1
→ Marrowline Phase 2 continuation #2
→ return/export
→ Loom revalidation / final inspectable state

Hostile assertions must include:

1. **Technical availability ≠ practical accessibility**: a visible button or HTTP 200 does not count if the operator cannot complete the task.
2. **Attempt completed ≠ need resolved**: each stage must achieve its declared stage-appropriate outcome.
3. **Closed status ≠ durable resolution**: reload/re-entry must preserve the right result, lineage and action support.
4. **Deflection ≠ resolution**: hiding, disabling or redirecting a broken path cannot be counted as success.
5. **Many transitions ≠ progress**: workflow churn/retries must not substitute for reduced distance to completion.
6. **Failure demand is measurable**: count avoidable retries, duplicate uploads, repeated imports, re-entry repairs, stale-stage recovery and manual workarounds created by prior failure.
7. **Event history remains reconstructable**: predecessor, stage, receiver, source revision and return relation survive.
8. **State compression is evidence-preserving**: compact UI/Portable AIA representations retain enough information to revalidate the consequential rule.
9. **Audit capacity keeps pace**: a completed execution may not outrun the verification needed to label it admitted.
