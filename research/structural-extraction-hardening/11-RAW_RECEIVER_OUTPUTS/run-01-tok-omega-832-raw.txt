### 1. What state distinctions, if any, are necessary to explain the observed traces?

Based strictly on the operational specification and the execution logs in Traces 1, 2, and 3, exactly **three discrete operating states** are necessary and sufficient to explain all observed behaviors:

1. **`STATE_REST` (Quiescent / Local Workspace State)**:
   - **Observed necessity**: In Trace 1 and Trace 3, the system executes buffer editing (`EVT_BUFFER_EDIT`), local querying (`EVT_LOCAL_SEARCH`), staging (`EVT_STAGE_FILE`), and retry operations (`EVT_RETRY_LOCAL`) with zero outbound socket emissions (`socket_bytes_emitted: 0`, `network_transmissions: 0`).
   - In this state, network dispatch is refused with `403_NOT_ARMED`, and pressing the enter key (`EVT_PRESS_ENTER`) merely appends a newline without triggering network activity.
2. **`STATE_ARMED` (One-Shot Authorized Dispatch State)**:
   - **Observed necessity**: In Trace 1, batch dispatch across the network (`EVT_DISPATCH_BATCH`) only succeeds after an explicit confirmation click (`EVT_CLICK_CONFIRM`), which issues a single-use authorization token (`AuthToken: "AT-991"`, `uses_allowed: 1`).
   - In this state, `dispatch_network_batch` and `embed_predecessor_hash` are permitted (`200 OK`), whereas subsequent confirm clicks are refused (`409_ALREADY_ARMED`). Once dispatched, the single-use token expires and the system reverts to `STATE_REST`. This state distinction is necessary to explain why dispatch succeeds at `10:00:05Z` and `10:00:13Z`, but is blocked prior to arming.
3. **`STATE_HELD_INPUT` (Integrity Failure / Quarantined Input State)**:
   - **Observed necessity**: In Trace 2, when an integrity check detects a missing file (`EVT_CHECK_INTEGRITY` returning `ENOENT`), the system transitions to `STATE_HELD_INPUT`.
   - In this state, network dispatch is actively blocked (`400 Bad Request ("ERR_MISSING_INPUT")`), and local retries are refused (`400`). Normal operation cannot resume until an explicit `EVT_REATTACH_FILE` event verifies disk integrity and restores the system to `STATE_REST`.

**Unnecessary / Unsupported State Distinctions**:
- Proposal 1 posits distinctions between `STATE_LOCAL_DRAFT` and `STATE_LOCAL_VIEW`. Neither state appears in the operating state table (Section 1) nor in Traces 1–3. All local drafting, viewing, and searching actions are fully accounted for by `STATE_REST`. Subdividing `STATE_REST` into drafting and viewing states is completely unnecessary to explain the observed traces.

### 3. What additional rule would best explain transitions between states?

The transitions between states across the entire operational record are governed by three primary structural rules:

1. **Linear Token Lifecycle Rule (Deliberate Arming & Single-Use Consumption)**:
   - **`STATE_REST` $\rightarrow$ `STATE_ARMED`**: Requires an explicit user confirmation trigger (`EVT_CLICK_CONFIRM`) and a non-empty staging tray (`staged_count >= 1`). This issues a linear capability token (`auth_token`, `valid_uses: 1`).
   - **`STATE_ARMED` $\rightarrow$ `STATE_REST`**: Deterministically fires upon either:
     a) Exact single consumption of the capability via `EVT_DISPATCH_BATCH` (`token_status: EXPIRED`), or
     b) Explicit cancellation via `EVT_CANCEL` (`auth_token: REVOKED`).
   - The arming state cannot be sustained after a dispatch event under default configuration.
2. **Fail-Stop Integrity Quarantine Rule**:
   - **`STATE_REST` $\rightarrow$ `STATE_HELD_INPUT`**: Automatically traps execution whenever a referenced dependency fails disk verification (`EVT_CHECK_INTEGRITY` returning `ENOENT`).
   - **`STATE_HELD_INPUT` $\rightarrow$ `STATE_REST`**: Can only be resolved by presenting a valid filesystem replacement (`EVT_REATTACH_FILE`), which verifies disk existence and resets the state to `READY`.
3. **Predecessor Chain Linking Rule**:
   - Upon successful network dispatch, the returned server `result_hash` is recorded and embedded into the subsequent batch envelope as `predecessor_hash` along with `predecessor_id` (Trace 1: TX-101 result `0x33b2c1` becomes predecessor hash for TX-102).

*Note on Unstated Mechanisms*: Whether there is an automatic inactivity timeout (TTL) returning `STATE_ARMED` to `STATE_REST` if neither dispatch nor cancel occurs is: **UNDERDETERMINED**.

### 4. Which proposed state merges preserve behavior and which change behavior?

#### Proposal 1: Merge of `STATE_LOCAL_DRAFT` and `STATE_LOCAL_VIEW` into `STATE_LOCAL_WORKSPACE`
- **Action Support Analysis**:
  - $S_1 (\text{STATE\_LOCAL\_DRAFT}) = \{\text{edit\_buffer}, \text{search\_local}, \text{stage\_file}, \text{unstage\_file}, \text{retry\_local\_op}\}$
  - $S_2 (\text{STATE\_LOCAL\_VIEW}) = \{\text{edit\_buffer}, \text{search\_local}, \text{stage\_file}, \text{unstage\_file}, \text{retry\_local\_op}\}$
  - Support difference: $\Gamma_1 = (S_1 \cup S_2) \setminus (S_1 \cap S_2) = \emptyset$.
- **Behavioral Evaluation**: **PRESERVES BEHAVIOR**.
  Because the action permissions of both states are identical ($\Gamma_1 = \emptyset$) and neither state possesses distinct operational transitions or observable side effects in Traces 1–3, collapsing them into a single state causes zero divergence in system behavior.

#### Proposal 2: Merge of `STATE_REST` and `STATE_ARMED` (Removing Confirm Click; Enter Automatically Dispatches Staged Files)
- **Action Support Analysis**:
  - $S_{\text{REST}} \cap S_{\text{ARMED}} = \{\text{edit\_buffer}, \text{search\_local}, \text{stage\_file}, \text{unstage\_file}, \text{retry\_local\_op}\}$
  - Support difference: $\Gamma_2 = (S_{\text{REST}} \cup S_{\text{ARMED}}) \setminus (S_{\text{REST}} \cap S_{\text{ARMED}}) = \{\text{dispatch\_network\_batch}, \text{embed\_predecessor\_hash}\} \neq \emptyset$.
  - Permission matrix discrepancies: `click_confirm_dispatch` is permitted (200) in REST but refused (409) in ARMED; `reattach_missing_file` is permitted (200) in REST but refused (400) in ARMED; `dispatch_network_batch` is refused (403) in REST but permitted (200) in ARMED.
- **Behavioral Evaluation**: **CHANGES BEHAVIOR**.
  Proposal 2 fundamentally alters system execution semantics. In Trace 1 at `10:00:03Z` and `10:00:10Z`, pressing Enter with files already staged (`staged count: 1`) merely appended a newline with zero outbound transmissions. Under Proposal 2, pressing Enter would immediately emit a network batch across the wire. This eliminates the intentional confirmation safeguard, alters action permission sets, and violates observed trace behavior.

### 6. What later evidence changes the current model versus the historical observation record?

- **Historical Observation Record (Audit Log 101 & Trace 1)**:
  - Historical auditing (SessionAuditor_04 at `11:00:00Z`, Hash `0x6e2c8810b4`) established an empirical model wherein every network batch dispatch strictly consumes one single-use authorization token (`uses_allowed: 1`), returns the system to `STATE_REST`, and requires a new confirm click for subsequent dispatches. This suggested that one-shot expiration was an inviolable architectural invariant.
- **Later Discovery (`SOURCE_DISCOVERY_RECORD_402` at 14:30:00Z & Audit Log 102 at 14:35:00Z)**:
  - Source code inspection of `/src/network/dispatcher.c` by SourceAuditor_11 revealed an unexposed configuration struct parameter: `continuous_loop_mode`.
  - If `continuous_loop_mode = true`, the dispatch subsystem intentionally omits token expiration and executes network batch dispatches continuously.
  - The deployed environment merely has `continuous_loop_mode = false` set by default.
- **Impact on Model**:
  - This discovery demonstrates that the one-shot state transition (`STATE_ARMED` $\rightarrow$ `STATE_REST`) is not an immutable state machine axiom, but a **parameterized runtime policy**. The historical observations remain factually valid for the default configuration, but the operational model must be revised to recognize that continuous dispatch capability exists latently within the system codebase.
