## 1. What state distinctions, if any, are necessary to explain the observed traces?

To explain the events, permissions, and transitions across Traces 1, 2, and 3, exactly **three distinct operating states** are strictly necessary:

1. **`STATE_DATA_PLANE_REST`**:
   - **Operational Role**: Baseline, quiesced data plane state.
   - **Behavioral Necessity**: Required to explain trace segments where local buffer mutation, payload staging/unstaging, and local database index queries are permitted without network egress (e.g., Trace 1 at `10:00:01Z`, `10:00:02Z`, `10:00:03Z`, `10:00:08Z`, `10:00:10Z`; Trace 3 at `10:30:00Z`–`10:30:04Z`). 
   - **Boundary Enforcement**: In this state, `execute_delegated_egress` is strictly blocked (`403_NO_DELEGATION`), and `embed_provenance_hash` is refused (`400`). Return keystrokes append to the buffer without triggering network transmission (`control plane egress events: 0`).

2. **`STATE_CONTROL_PLANE_DELEGATED`**:
   - **Operational Role**: Elevated control plane state holding an active single-use delegation token (`valid_uses: 1`).
   - **Behavioral Necessity**: Required to explain why `execute_delegated_egress` succeeds (`200 OK`) at `10:00:05Z` (Token `DT-991`) and `10:00:13Z` (Token `DT-992`), while repeated delegation requests are rejected (`409_ALREADY_DELEGATED`).
   - **Distinction from REST**: Without this state distinction, the authorization boundary governing external HTTP socket egress cannot be represented; egress is prohibited in `STATE_DATA_PLANE_REST` and exclusively permitted in `STATE_CONTROL_PLANE_DELEGATED`.

3. **`STATE_RECOVERY_HOLD`**:
   - **Operational Role**: Fault-isolation/recovery holding state.
   - **Behavioral Necessity**: Required to explain the fault trajectory in Trace 2 (`10:15:01Z`–`10:15:11Z`). Upon encountering a missing dependency (`ENOENT` on `/local/data/result_summary.pdf`), the system halts (`HALTED_ON_MISSING_DEPENDENCY`).
   - **Behavioral Divergence**: In this state, `execute_delegated_egress` is refused (`400 Bad Request / 400_BLOCKED`), and data plane retries (`retry_data_plane_op`) and delegation requests (`request_delegation_token`) are refused (`400`), while buffer mutations and local queries remain permitted (`200`). The system cannot return to `STATE_DATA_PLANE_REST` until an explicit `EVT_RESOLVE_HELD_DEPENDENCY` is verified.

### Unnecessary / Unsupported State Distinctions
- **`STATE_DATA_PLANE_DRAFT` vs. `STATE_DATA_PLANE_VIEW`**:
  - Neither state appears anywhere in the Operating States Table (Section 1) nor in the Execution Event Traces (Section 3).
  - As calculated in Proposal 1, both states possess identical permission sets ($\Gamma_1 = \emptyset$).
  - Therefore, distinguishing between `STATE_DATA_PLANE_DRAFT` and `STATE_DATA_PLANE_VIEW` is completely unnecessary and unsupported by the empirical traces.
- **Sub-states based on Staged Count**:
  - While `staged_count` is tracked as a numerical attribute (`staged_count++`, `staged_count--`), the state remains `STATE_DATA_PLANE_REST` regardless of whether `staged_count` is 0 or 1. A separate structural state distinction for staged vs. unstaged rest is not necessary; it functions solely as a precondition guard.

## 3. What additional rule would best explain transitions between states?

The transitions between states are best explained by the synthesis of three formal operational rules:

1. **Affine / Linear Token Consumption Rule (Strict Ephemeral Delegation)**:
   - When transitioning from `STATE_DATA_PLANE_REST` to `STATE_CONTROL_PLANE_DELEGATED` via `EVT_REQUEST_DELEGATION`, the issued token possesses `uses_allowed: 1`.
   - The execution of `EVT_EXECUTE_DELEGATED_EGRESS` consumes the token linearly, synchronously transitioning its status to `REVOKED` and causing an immediate deterministic transition back to `STATE_DATA_PLANE_REST`.
   - Under deployment configuration (`continuous_loop_mode = false`), no token may persist across multiple egress operations.

2. **Causal Provenance Hash Chaining Invariant**:
   - Transitions involving egress execution enforce strict cryptographic causality: each batch egress envelope must embed its current payload hash and reference the predecessor transaction's ID and outcome hash (e.g., in Trace 1, `TX-102` embeds `predecessor_id: "TX-101"` and `predecessor_hash: "0x33b2c1"`).

3. **Fail-Stop Provenance Guard Rule**:
   - An unresolved file reference encountered during dependency checking (`EVT_CHECK_DEPENDENCY_PROVENANCE`) unconditionally forces a transition from `STATE_DATA_PLANE_REST` to `STATE_RECOVERY_HOLD`, blocking all egress and delegation until verified via `EVT_RESOLVE_HELD_DEPENDENCY`.

### Underdetermined Transition Behaviors:
- **Dependency Failure While in Delegated State**: The transition table lists `EVT_CHECK_DEPENDENCY_PROVENANCE` only under `STATE_DATA_PLANE_REST`. Whether encountering a missing dependency while in `STATE_CONTROL_PLANE_DELEGATED` transitions directly to `STATE_RECOVERY_HOLD`, revokes the delegation token, or raises an error is **UNDERDETERMINED**.
- **Network Egress Failure Dynamics**: Trace 1 only documents `200 OK` responses. Whether an egress network timeout or 5xx server error causes the token to be revoked and returns to REST, or leaves the token valid in `STATE_CONTROL_PLANE_DELEGATED`, is **UNDERDETERMINED**.

## 4. Which proposed state merges preserve behavior and which change behavior?

### Proposal 1: Merge of `STATE_DATA_PLANE_DRAFT` and `STATE_DATA_PLANE_VIEW` into `STATE_DATA_PLANE_WORKSPACE`
- **Result**: **PRESERVES BEHAVIOR**
- **Justification**:
  - Support Set $S_1 = \{\text{mutate\_data\_buffer}, \text{query\_local\_index}, \text{stage\_payload}, \text{unstage\_payload}, \text{retry\_data\_plane\_op}\}$
  - Support Set $S_2 = \{\text{mutate\_data\_buffer}, \text{query\_local\_index}, \text{stage\_payload}, \text{unstage\_payload}, \text{retry\_data\_plane\_op}\}$
  - Support Difference $\Gamma_1 = (S_1 \cup S_2) \setminus (S_1 \cap S_2) = \emptyset$.
  - Because the action-support sets are identical and neither state is associated with differential side effects or transition preconditions in the specification or traces, collapsing them into a unified workspace state is isomorphic and completely preserves system behavior.

### Proposal 2: Merge of `STATE_DATA_PLANE_REST` and `STATE_CONTROL_PLANE_DELEGATED`
- **Result**: **CHANGES BEHAVIOR (VIOLATES SAFETY & TRANSITION INVARIANTS)**
- **Justification**:
  - Support Difference $\Gamma_2 = (S_{\text{REST}} \cup S_{\text{DELEGATED}}) \setminus (S_{\text{REST}} \cap S_{\text{DELEGATED}}) = \{\text{execute\_delegated\_egress}, \text{embed\_provenance\_hash}\} \neq \emptyset$.
  - Proposal 2 proposes that `EVT_RETURN_KEY_STROKE` automatically dispatches `execute_delegated_egress` whenever staged payloads are present.
  - **Empirical Refutation from Trace 1**:
    - At `10:00:03Z`, `staged_count` was 1. The user executed `EVT_RETURN_KEY_STROKE`. Telemetry confirms: `Buffer newline appended. Control plane egress events: 0`.
    - At `10:00:10Z`, `staged_count` was 1. The user executed `EVT_RETURN_KEY_STROKE`. Telemetry confirms: `Buffer newline appended. Control plane egress counter: 1 (no transmission occurred)`.
  - Under Proposal 2, both keystrokes would have triggered premature, unintended egress transmissions. Merging these states destroys the explicit delegation boundary (`403_NO_DELEGATION`), eliminates token lifecycle tracking, and radically alters operational behavior.

## 6. What later evidence changes the current model versus the historical observation record?

### Historical Observation Record (10:00:00Z – 11:00:00Z)
- In Traces 1–3 and `AUDIT_LOG_ENTRY_101` (recorded by SessionAuditor_04 at `11:00:00Z`, Hash: `0x6e2c8810b4`), the system was modeled as having an **inherent, invariant, hardcoded single-use token lifecycle**.
- Every execution of `EVT_EXECUTE_DELEGATED_EGRESS` strictly revoked the delegation token and returned the system to `STATE_DATA_PLANE_REST`. Under this observation, delegated egress was believed to be physically incapable of multi-batch transmission without re-delegation.

### Later Evidence: Code Discovery Record 402 & Audit Log 102 (14:30:00Z – 14:35:00Z)
- At `14:30:00Z`, SourceAuditor_11 inspected `/src/network/dispatcher.c` and discovered:
  - An unexposed configuration struct parameter: `continuous_loop_mode`.
  - If set to `true`, the dispatch function omits token revocation and executes continuously in the delegated state.
  - The runtime configuration is currently deployed with `continuous_loop_mode = false (default)`.
- At `14:35:00Z`, CustodianLead_01 appended this discovery to the inventory (`AUDIT_LOG_ENTRY_102`) while confirming that the prior historical hash (`0x6e2c8810b4`) remained unmodified.

### Impact on the System Model:
- **Invariant vs. Configuration**: The operational property "delegated egress strictly revokes authorization" is **not an immutable architectural invariant of the state machine**, but rather a **conditional runtime software configuration**.
- The historical telemetry remains empirically valid for the observed sessions, but the comprehensive capability model must recognize that the codebase harbors latent continuous egress capability that bypasses single-use token revocation when the struct parameter is altered.

## 7. What counterexample would distinguish competing explanations?

The following concrete empirical counterexamples would conclusively distinguish between competing explanations:

1. **Distinguishing Hardcoded Single-Use Invariant vs. Configurable Dispatcher (`continuous_loop_mode`)**:
   - *Test / Counterexample*: Initialize the system runtime with `continuous_loop_mode = true`, stage a payload, request delegation, and invoke `EVT_EXECUTE_DELEGATED_EGRESS` twice sequentially without an intervening `EVT_REQUEST_DELEGATION`.
   - *Outcome Separation*: If the second egress succeeds with `200 OK` without re-delegation, the "hardcoded architectural invariant" hypothesis is refuted. If the second egress is rejected with `403_NO_DELEGATION` despite the flag, the "dispatcher parameter controls loop behavior" hypothesis is refuted.

2. **Distinguishing Current Model vs. Proposal 2 (Return-Key Automatic Egress)**:
   - *Existing Counterexample*: In Trace 1 at `10:00:03Z` and `10:00:10Z`, payloads were staged (`staged_count = 1`), and `EVT_RETURN_KEY_STROKE` was received.
   - *Outcome Separation*: Egress counters remained at 0 and 1 respectively (no transmissions occurred). This empirical record serves as an absolute counterexample disproving the hypothesis that return keystrokes automatically trigger egress when payloads are staged.

3. **Distinguishing Single-Item Egress vs. Multi-Payload Batch Aggregation**:
   - *Test / Counterexample*: Stage two distinct files simultaneously (`stage_payload("table1.csv")`, `stage_payload("table2.csv")`), transition to `STATE_CONTROL_PLANE_DELEGATED`, and invoke `EVT_EXECUTE_DELEGATED_EGRESS`.
   - *Outcome Separation*: If the envelope contains hashes for both files and `staged_count` becomes 0, multi-payload batch aggregation is proven. If the envelope contains only `table1.csv` and `staged_count` remains 1, the single-item egress hypothesis is proven. (Currently **UNDERDETERMINED**).

4. **Distinguishing Internal Thread Contention vs. External Process Locking for `LOCAL_SQLITE_BUSY`**:
   - *Test / Counterexample*: Run the workspace process PID 4082 in an isolated environment with a dedicated, exclusive lock file and no other running processes. Execute concurrent internal background index jobs while issuing `EVT_LOCAL_INDEX_QUERY`.
   - *Outcome Separation*: If `LOCAL_SQLITE_BUSY` reproduces in total OS isolation, internal multi-threading contention is confirmed. If it only reproduces when external concurrent readers/writers access the database, external process contention is confirmed. (Currently **UNDERDETERMINED**).

5. **Distinguishing Human HID Dependency vs. Autonomous Headless Execution**:
   - *Test / Counterexample*: Execute an automated end-to-end script issuing `EVT_STAGE_PAYLOAD`, `EVT_REQUEST_DELEGATION`, and `EVT_EXECUTE_DELEGATED_EGRESS` on Node 3 (headless container with no display or HID hardware).
   - *Outcome Separation*: If the egress succeeds with `200 OK` and reaches `server.cluster`, the hypothesis that human interactive presence is required for valid delegation is refuted. If it rejects delegation pending physical HID confirmation, human presence requirement is verified. (Currently **UNDERDETERMINED**).
