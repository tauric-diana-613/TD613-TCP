## 1. What state distinctions, if any, are necessary to explain the observed traces?

Based on the execution traces (Traces 1, 2, and 3) and the Action-Permission Matrix, exactly **three discrete states** are necessary and sufficient to account for all observed system behaviors: `STATE_SIGMA_0`, `STATE_SIGMA_1`, and `STATE_SIGMA_2`.

```mermaid
stateDiagram-v2
    [*] --> STATE_SIGMA_0
    STATE_SIGMA_0 --> STATE_SIGMA_1 : OP_OMEGA_TAU (Staged items >= 1)
    STATE_SIGMA_1 --> STATE_SIGMA_0 : OP_OMEGA_PHI (200 OK / Token Revoked)
    STATE_SIGMA_1 --> STATE_SIGMA_0 : OP_NULLIFY (Token Nullified)
    STATE_SIGMA_0 --> STATE_SIGMA_2 : OP_CHECK_VECTOR_NU (Dependency missing)
    STATE_SIGMA_2 --> STATE_SIGMA_0 : OP_LAMBDA_RHO (Vector resolved)
    STATE_SIGMA_2 --> STATE_SIGMA_2 : OP_OMEGA_PHI (Rejected: 400 Bad Request)
```

### Necessary Distinctions:

1. **`STATE_SIGMA_0` (Baseline / Staging & Local Operations) vs. `STATE_SIGMA_1` (Armed / Dispatch State)**:
   - **Permission Boundary**: In `STATE_SIGMA_0`, the egress action `action_omega_phi` is strictly `REFUSED (403_NO_TOKEN)`. Conversely, in `STATE_SIGMA_1`, `action_omega_phi` is `PERMITTED (200)`, whereas re-arming via `action_omega_tau` is `REFUSED (409_ALREADY_ACTIVE)`.
   - **Observable Egress Invariant**: In Trace 1, local mutations (`OP_PSI_ALPHA`, `OP_PSI_GAMMA`, `OP_KEY_STROKE`) execute exclusively in `STATE_SIGMA_0` with `channel_zeta_egress: 0 bytes`. External transmission across Channel Zeta occurs exclusively during `OP_OMEGA_PHI` while in `STATE_SIGMA_1`.
   - **Token Gating**: `STATE_SIGMA_1` represents an armed execution context holding an active single-use token (`token_zeta: issued (valid_uses: 1)`). Once consumed or revoked (`REVOKED_CHI`), the system cannot remain in `STATE_SIGMA_1` and drops back to `STATE_SIGMA_0`.

2. **`STATE_SIGMA_0` (Operational Baseline) vs. `STATE_SIGMA_2` (Halted / Dependency Deficit)**:
   - **Operational Blockade**: In Trace 2, failure of a required path check (`ENOENT` on `/local/data/result_summary.pdf`) transitions the system into `STATE_SIGMA_2` (`HALTED_ON_DEPENDENCY_DEFICIT`).
   - **Deficit Enforcement**: While in `STATE_SIGMA_2`, attempting dispatch via `OP_OMEGA_PHI` fails immediately with `400 Bad Request ("ERR_MISSING_INPUT")` (`REFUSED 400_BLOCKED`), and `action_psi_epsilon` and `action_omega_tau` are `REFUSED (400)`.
   - **Resolution Invariant**: Normal operations cannot resume until verification occurs via `OP_LAMBDA_RHO` (`status: VECTOR_VERIFIED`), transitioning the system back to `STATE_SIGMA_0`.

3. **Absence of Other Necessary States in Traces**:
   - The execution records contain no traces of `STATE_SIGMA_DRAFT` or `STATE_SIGMA_VIEW` (mentioned only in Proposal 1). Collapsing or distinguishing states outside of $\{ \text{STATE\_SIGMA\_0}, \text{STATE\_SIGMA\_1}, \text{STATE\_SIGMA\_2} \}$ is neither supported nor required by the observed traces.

## 3. What additional rule would best explain transitions between states?

The observed state dynamics are best explained by **two formal operational rules**:

### Rule A: Strict Linear Token Consumption (Affine State Invariant)
The duration of residence in `STATE_SIGMA_1` is strictly governed by the consumption lifecycle of `token_zeta`:
$$\text{State}(\tau) = \text{STATE\_SIGMA\_1} \iff \text{TokenZeta}(\tau).\text{valid\_uses} = 1 \land \text{TokenZeta}(\tau).\text{status} = \text{ACTIVE}$$
- `OP_OMEGA_TAU` creates a token with capacity $1$.
- Any transmission event (`OP_OMEGA_PHI`) or explicit abort (`OP_NULLIFY`) consumes or revokes the token, resetting capacity to $0$ (`REVOKED_CHI` / `NULLIFIED`).
- The transition back to `STATE_SIGMA_0` is immediate and deterministic upon token exhaustion. No operation can remain in `STATE_SIGMA_1` once `valid_uses` drops to $0$.

### Rule B: Causal Cryptographic Hash-Chaining of Sequential Envelopes
Transitions through `STATE_SIGMA_1` generate sequentially linked execution payloads:
- In Trace 1, envelope `TX-101` (`payload_hash: "0x7a8f11"`) yielded server response `outcome_hash: "0x33b2c1"` with `predecessor_id: null`.
- The subsequent dispatch `TX-102` (`payload_hash: "0x55d04e"`) explicitly embedded:
  $$\text{predecessor\_id} = \text{"TX-101"}, \quad \text{predecessor\_hash} = \text{"0x33b2c1"}$$
- **Rule**: Every successful transition cycle $\text{STATE\_SIGMA\_0} \xrightarrow{\text{OP\_OMEGA\_TAU}} \text{STATE\_SIGMA\_1} \xrightarrow{\text{OP\_OMEGA\_PHI}} \text{STATE\_SIGMA\_0}$ must bind the previous transaction's terminal outcome hash into the next transaction's dispatch envelope, forming a directed acyclic lineage.

*(Note: The internal scheduling engine determining whether vector path verification `OP_CHECK_VECTOR_NU` occurs synchronously or asynchronously is **UNDERDETERMINED**).*

## 4. Which proposed state merges preserve behavior and which change behavior?

### Proposal 1: Merge `STATE_SIGMA_DRAFT` and `STATE_SIGMA_VIEW` into `STATE_SIGMA_WORKSPACE`
- **Behavioral Impact**: **PRESERVES BEHAVIOR** (at the action-permission layer).
- **Formal Justification**:
  - Action support sets:
    $$\mathcal{S}_1 = \mathcal{S}_2 = \{ \text{action\_psi\_alpha}, \text{action\_psi\_beta}, \text{action\_psi\_gamma}, \text{action\_psi\_delta}, \text{action\_psi\_epsilon} \}$$
  - The symmetric difference (support difference) is strictly empty:
    $$\Gamma_1 = \mathcal{U}_1 \setminus \mathcal{I}_1 = \emptyset$$
  - Because both states admit the exact same set of operations and neither state appears in the active transition table or execution logs, collapsing them introduces no action-permission discrepancies.
  - *Caveat*: Whether internal display semantics or rendering properties differ between draft and view modes is **UNDERDETERMINED**, but externally observable action permissions remain identical.

### Proposal 2: Merge `STATE_SIGMA_0` and `STATE_SIGMA_1` (Collapsing Arming and Dispatch)
- **Behavioral Impact**: **CHANGES BEHAVIOR** (fundamentally and destructively).
- **Formal Justification**:
  - The action support difference is non-empty:
    $$\Gamma_2 = \mathcal{U}_2 \setminus \mathcal{I}_2 = \{ \text{action\_omega\_phi}, \text{action\_omega\_chi} \} \neq \emptyset$$
  - Under the current architecture, `action_omega_phi` is strictly refused in `STATE_SIGMA_0` (`403_NO_TOKEN`), and `OP_KEY_STROKE` in `STATE_SIGMA_0` never causes egress (Trace 1: 10:00:03Z and 10:00:10Z both record `External egress events: 0` despite staged files being present).
  - Proposal 2 eliminates `OP_OMEGA_TAU` and automatically fires `action_omega_phi` upon an `OP_KEY_STROKE` whenever `staged_count >= 1`.
  - Under Proposal 2:
    1. Typing a newline in Trace 1 (10:00:03Z) would immediately transmit `table1.csv` across Channel Zeta without the explicit token issuance step.
    2. In Trace 3, where `confidential_notes.txt` was placed in the staging tray at 10:30:00Z, any subsequent keystroke would cause premature external egress of confidential data.
  - Proposal 2 destroys the authorization boundary, bypasses single-use token issuance, and alters egress frequency and conditions.

## 6. What later evidence changes the current model versus the historical observation record?

The critical divergence occurs between **AUDIT_LOG_ENTRY_101** (11:00:00Z) and **SOURCE_DISCOVERY_RECORD_402** (14:30:00Z):

```mermaid
flowchart LR
    A["Historical Model (Audit Log 101)<br/>• Egress strictly single-shot<br/>• Token nullification mandatory<br/>• Structural invariant: Return to S0"]
    B["Source Discovery 402<br/>• dispatcher.c has 'continuous_loop_mode'<br/>• If true: Token nullification omitted<br/>• Egress executes continuously"]
    C["Updated Model (Audit Log 102)<br/>• Single-shot egress is a runtime default, not a hardware/architectural limit<br/>• Latent streaming capability exists"]
    A -->|Inspection of /src/network/dispatcher.c| B -->|Audit Appended| C
```

1. **Historical Observation Model (`AUDIT_LOG_ENTRY_101`)**:
   - Inspector `SessionAuditor_04` documented an immutable single-dispatch lifecycle: `OP_OMEGA_TAU` issued once, TX-101 dispatched, exactly 1 Channel Zeta egress event occurred, token revoked, returned to `STATE_SIGMA_0`.
   - Based purely on historical execution, the single-token egress model appeared to be a rigid, hardcoded structural topology constraint of the system.

2. **Later Evidence (`SOURCE_DISCOVERY_RECORD_402` & `AUDIT_LOG_ENTRY_102`)**:
   - Static analysis of `/src/network/dispatcher.c` revealed an unexposed struct parameter: `continuous_loop_mode`.
   - When set to `true`, dispatch **omits token nullification** and sustains continuous execution in the egress state.
   - The current production setting `continuous_loop_mode = false` is merely a default configuration, not an unalterable structural constraint.

3. **Model Shift**:
   - The model shifts from an **architecturally bounded finite state machine** (where multi-egress without re-arming is physically impossible) to a **configuration-governed policy framework** (where continuous looping egress is architecturally supported in code, but suppressed by deployment flags).
   - `AUDIT_LOG_ENTRY_102` verifies that the prior audit log hash (`0x6e2c8810b4`) was unchanged, confirming that this was a discovery of latent latent code capability rather than a retroactive tampering with execution history.

## 7. What counterexample would distinguish competing explanations?

To resolve the competing explanations identified across the specification, the following concrete counterexamples and empirical test scenarios are specified:

### Counterexample A: Distinguishing Token-Gated Single-Shot Model vs. Proposal 2 Automatic Egress
* **Competing Explanations**:
  - *Hypothesis 1 (Current Topology)*: External egress requires an explicit transition to `STATE_SIGMA_1` via `OP_OMEGA_TAU` issuing a single-use token. Keystrokes in `STATE_SIGMA_0` never trigger egress.
  - *Hypothesis 2 (Proposal 2)*: `OP_KEY_STROKE` automatically invokes `action_omega_phi` whenever staged items are present.
* **Test Protocol / Counterexample**:
  1. In `STATE_SIGMA_0`, execute `OP_PSI_GAMMA` with `/local/data/table1.csv` (`staged_count = 1`).
  2. Input an `OP_KEY_STROKE` event without invoking `OP_OMEGA_TAU`.
* **Observable Discrimination**:
  - Under **Hypothesis 1**: `channel_zeta_egress` remains 0 bytes; `egress_counter` remains unchanged; state remains `STATE_SIGMA_0`. (Observed and confirmed in Trace 1 at 10:00:03Z and 10:00:10Z).
  - Under **Hypothesis 2**: Channel Zeta socket transmits payload `TX-101`; egress counter increments to 1.
  - *Result*: The observed traces directly provide this counterexample, conclusively refuting Hypothesis 2.

### Counterexample B: Distinguishing Hard Architectural Invariant vs. Latent Configuration Parameter for Egress Looping
* **Competing Explanations**:
  - *Hypothesis 1 (Hard Architectural Constraint)*: The finite state topology cannot execute multiple dispatches without transitioning back to `STATE_SIGMA_0` and acquiring a new token.
  - *Hypothesis 2 (Configurable Policy Flag)*: Setting `continuous_loop_mode = true` allows consecutive dispatches without dropping to `STATE_SIGMA_0` or nullifying tokens.
* **Test Protocol / Counterexample**:
  1. In a sandbox environment (e.g., Host X-30), initialize `/src/network/dispatcher.c` with `continuous_loop_mode = true`.
  2. Execute `OP_PSI_GAMMA` (stage 2 items) followed by `OP_OMEGA_TAU` to enter `STATE_SIGMA_1`.
  3. Execute `OP_OMEGA_PHI` (first payload TX-101).
  4. Immediately execute a second `OP_OMEGA_PHI` (second payload TX-102) without an intervening `OP_OMEGA_TAU`.
* **Observable Discrimination**:
  - Under **Hypothesis 1**: The second `OP_OMEGA_PHI` fails with `403_NO_TOKEN` (or `400_BLOCKED`), because the state transitioned to `STATE_SIGMA_0` and token status became `REVOKED_CHI`.
  - Under **Hypothesis 2**: The second `OP_OMEGA_PHI` returns HTTP 200 OK, `egress_counter` increments to 2, and the system remains in `STATE_SIGMA_1`.

### Counterexample C: Distinguishing True Operational Distinction between `STATE_SIGMA_DRAFT` and `STATE_SIGMA_VIEW`
* **Competing Explanations**:
  - *Hypothesis 1 (Behaviorally Isomorphic / Redundant)*: `STATE_SIGMA_DRAFT` and `STATE_SIGMA_VIEW` possess identical operational semantics; Proposal 1's collapse is functionally transparent.
  - *Hypothesis 2 (Internal Latent Asymmetry)*: S1 and S2 differ in write-permission side effects or internal state attributes.
* **Test Protocol / Counterexample**:
  1. Initialize the system in `STATE_SIGMA_VIEW`.
  2. Attempt a state-modifying operator: `OP_PSI_ALPHA` (length increment) or `OP_PSI_GAMMA` (stage item).
* **Observable Discrimination**:
  - Under **Hypothesis 1**: Modification succeeds with `length_counter++` or `staged_count++`, matching draft behavior.
  - Under **Hypothesis 2**: The modification is rejected (e.g., read-only refusal) or forces an undocumented state transition to `STATE_SIGMA_DRAFT`.
  - *Current Status*: Because no execution traces exist for S1 and S2, this determination remains **UNDERDETERMINED** until such a test is executed.
