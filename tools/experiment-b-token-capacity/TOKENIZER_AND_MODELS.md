# Tokenizer, model and effort profiles

The implementation uses real js-tiktoken 1.0.21, with package-lock integrity. It reconstructs the reference rank-file bytes and verifies official SHA-256 for o200k_base and cl100k_base. Pattern identity, implementation version and maximum token-byte length are recorded privately. Known-token vectors and Unicode tests exercise the actual encoders; no byte/character heuristic or fake tokenizer is substituted for exact local counts.

Exactness is relative to the pinned implementation and recorded JavaScript/Unicode runtime in runtime-profile.json. Equivalent behavior across different regex engines or Unicode versions is not independently proved. A future host must verify the complete artifact manifest and freeze the runtime as part of its approved custody setup; table identity alone does not authenticate an upstream provider's tokenizer implementation.

The pinned [official tokenizer registry](https://github.com/openai/tiktoken/blob/4e71bbe0c078468e00fefbf94b39849389f346e5/tiktoken/model.py) has no GPT-6.1 Sol mapping. Its [encoding definitions](https://github.com/openai/tiktoken/blob/4e71bbe0c078468e00fefbf94b39849389f346e5/tiktoken_ext/openai_public.py) publish the reference rank hashes. Consequently the demo labels its encoding o200k_base and model mapping unverified; it does not assert that reference encoding is the served GPT-6.1 Sol tokenizer.

Two future profile bases are supported: a matching mapping in the pinned package registry, or an explicitly operator-accepted offline mapping with a cited evidence reference. Both require a model-specific profile, declared supported efforts, context and output limits, matching rank/pattern hashes, and a profile digest bound into the signed offline decision. Registry lookup never silently substitutes a nearby model. Unknown mappings, unsupported encoding implementations and efforts not listed by the profile refuse. No profile here independently attests provider behavior.

The instrument's public model-ID set includes the proposed GPT-6 family and selected registry-known model names. Membership is input validation, not an availability claim or a recommendation to substitute a model. Only the two implemented reference encodings are supported. A new tokenizer requires a reviewed new version, not a runtime download. A future evaluator can use a different reference encoding; an independent evaluator's actual model/profile remains separately required.

Changing effort alone does not change a fixed text's BPE count under a fixed encoding. Future reasoning, outputs, visible delimiters, orchestration and provider framing may vary with model and effort. They remain unknown or explicitly assumed. Medium-request rates from #1616 are not High observations or measurements of another model. No model choice is adopted and no new model turn was made in this commission.

The [official token-counting guidance](https://developers.openai.com/api/docs/guides/token-counting) distinguishes local text counts from provider formatting and non-visible generated tokens. This instrument does not call its hosted endpoint or transmit an input. Complete provider input and future reasoning totals remain unmeasured.
